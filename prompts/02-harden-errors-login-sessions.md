# 02 · Harden errors, login, and sessions

## Context
Single-user, self-hosted Go app (`internal/app/server.go`) with a shared password, HMAC-signed `nc_session` cookies, and a SQLite-backed login limiter. It is meant to sit behind an HTTPS reverse proxy. Errors flow through `httpError` and `(*App).fail`. The password hash (`passwordKey`, PBKDF2 600k) is computed at startup and compared in constant time on login.

## Problems found (verified at `4bafb11`)
1. **Global login lockout.** `login()` counts every POST from every client in `login_attempts` (no client column) and returns 429 at 10 per minute. Anyone who can reach the app can lock the owner out with 10 requests a minute, and successful logins also count. `TestDemoAndLoginLimit` currently **asserts** this: after 10 wrong passwords the *correct* password gets a 429.
2. **Stateless sessions.** `logout` just sets a fresh unauthenticated cookie. A copied authenticated cookie stays valid for 7 days. Changing `APP_PASSWORD` does not invalidate existing sessions (the cookie is signed only with `APP_SECRET_KEY`, and the password is not bound into it).
3. **No request identity on errors.** `fail()` logs 5xx with `log.Printf("%s %s: %v")` and shows a generic message. There is no request ID shown to the user and none in the log line, so a user report cannot be matched to a log entry. Panics in handlers are caught by `net/http`'s default recover, which logs a stack with no context and drops the connection with no friendly page.
4. **Missing response headers.** No `Strict-Transport-Security` when `COOKIE_SECURE=1`, and no `Permissions-Policy`.
5. **Unclear 400 for stale forms.** The middleware gives any POST whose CSRF value does not match the same message ("Your form expired…"), including the case where the browser sent no valid session cookie at all (restart with a new `APP_SECRET_KEY`, expired cookie, cookies blocked). Note that the middleware silently issues a new anonymous session in that case, so the next request "works" with no explanation.
6. **Login is CPU-expensive and unthrottled per client.** Each attempt costs one PBKDF2 (600k iterations). The limiter's DB write happens first, which is good, but the limit being global is also the only protection. A per-client limit plus a global ceiling gives both fairness and a CPU cap.

Already fine (do not redo): user-facing validation errors are typed (`bad`, `conflict`), so there is no catch-all that exposes internal text. Keep it that way.

## Task
1. **Per-client limiter.** Key on the client IP. Use `r.RemoteAddr` (via `net.SplitHostPort`) by default. Add an opt-in `TRUSTED_PROXY_HOPS` env var (default `0`, parsed in `cmd/next-chapter/main.go`, passed through `Config`): when `N > 0`, take the Nth entry from the **right** of `X-Forwarded-For`, falling back to `RemoteAddr` if the header is shorter. Never trust the header otherwise. Document in README that behind a proxy the operator must set it, and what happens if they do not (all clients share the proxy's IP and one limit). Count only **failed** attempts. Add a global backstop (about 100 failures/minute) that returns 429 only when exceeded, and make sure a client under its own limit is not blocked by another client's failures unless that backstop trips. Return a `Retry-After` header (extend `httpError` or add a sibling type that can carry headers).
2. **Request IDs and a real 500 path.** Generate a short random ID per request in the outer handler and store it in `requestState`. Log every 5xx as `request_id=… method=… path=… err=…` (use `log/slog` text handler or plain `log`; do not log query strings, form values, or cookies). Show the ID on `error.html` for 5xx. Add a `recover` wrapper in the outer handler that logs the panic value and stack with the ID and renders the same page with status 500.
3. **Revocable sessions.** Add a `session_epoch` (random token in `meta`, created on first run). Put a value derived from `HMAC(Secret, epoch ‖ SHA-256(passwordKey))` into the session payload on login; verify it on every request and treat a mismatch as unauthenticated. Rotating the epoch or changing `APP_PASSWORD` then invalidates old sessions. Do not store the password or its hash in the database or the cookie. Keep `/logout` behavior, and add "Sign out everywhere" in Preferences that rotates the epoch (CSRF + revision check; it must not bump the library revision, since it is not a library change). Demo mode has no login; keep it working.
4. **Headers.** Add `Strict-Transport-Security: max-age=31536000; includeSubDomains` only when `SecureCookie` is true, and `Permissions-Policy: camera=(), microphone=(), geolocation=()` always. Keep the existing CSP, `X-Frame-Options`, and `Cache-Control` behavior (static assets stay cacheable).
5. **CSRF message.** Distinguish "no valid session" (say the session expired or was reset and to reload) from "token mismatch" (current text). Do this without setting a new session cookie on a failing POST to a non-login path unnecessarily; keep the behavior that the user gets a fresh working session after reloading.

## Schema
The limiter needs a client column. Use the migration framework from prompt 05 if it exists. If not, create a **new** table `login_failures(client TEXT NOT NULL, at REAL NOT NULL)` with `CREATE TABLE IF NOT EXISTS` in `schema.sql` and leave `login_attempts` in place, then say so in the report. `Store.Backup()` must keep scrubbing every limiter table, and the `session_epoch` should not be copied into backups meant for restore elsewhere (a restore should start with a new epoch; decide, implement, and justify).

## Acceptance criteria
- Update `TestDemoAndLoginLimit` to the new semantics. New tests: client A exhausting its limit does not block client B (set `req.RemoteAddr`); a successful login does not count; correct password still works for a client under its limit; the global backstop trips; `Retry-After` is present on 429; with `TRUSTED_PROXY_HOPS=1`, a spoofed leftmost `X-Forwarded-For` entry is ignored and without it the header is ignored entirely; a panicking handler yields a 500 page containing a request ID and a log line with the same ID; rotating the epoch invalidates an existing authenticated cookie; changing the password (new `App` on the same DB with a different password) invalidates it; HSTS appears only with `SecureCookie`; CSRF failure messages differ for missing session vs bad token.
- All other existing tests pass.

## Out of scope
Multi-user accounts, OAuth, password reset.
